# v0.5 Migration Plan — Code Meets Docs

## Goal

Bring the implementation into alignment with `docs/prd` and `docs/adr`. Every concrete claim those documents make should be verifiable in the running code.

This is a migration plan, not implementation. Sign-off on this document gates the start of Phase 0.

## Branch & PR strategy

- `v0.5` is a long-lived integration branch off `main`.
- Each phase below ships as one feature branch → PR into `v0.5`.
- Squash-merge phases into `v0.5` to keep history scannable.
- `v0.5` → `main` only after Phase 8 sign-off.
- **Phase rollback policy.** If a phase regresses against the prior phase's baseline — convergence-fixture assertions, Phase 0 snapshots the engineer can't justify, or a user-perceived metric in the PRD — **revert the merge** on `v0.5` and reopen the phase spec. Do not fix forward; that hides the regression in subsequent diffs. The convergence fixture (Phase 3) and Phase 0 snapshots are the canonical baselines. Record any deliberate deviation in the ADR.

## Phase ordering

Dependency-ordered (not chronological — Phase 4 can run parallel to 2/3).

```
0. Safety net  ─►  1. Schema  ─►  2. Module split  ─►  3. Algorithm  ─►  5. Worker
                       │                                    │
                       └──────────►  4. Parsers              └──►  6. Edit parity
                                                                      │
                                                            7. Docs ──┴──► 8. Coverage
```

## Locked decisions

1. **localStorage migration on first v0.5 boot — rollback-safe.** Single user, single browser. Read the legacy `hockey-scheduler-state` blob, rebuild team IDs, resolve game `homeTeam`/`awayTeam` names → IDs by lookup, then **atomically**:
   1. Copy the legacy blob to `hockey_legacy_backup` (kept for one boot as insurance).
   2. Write the four new keys per ADR §8.
   3. Re-read all four new keys and JSON-parse to verify integrity.
   4. Only on successful verification, delete the original `hockey-scheduler-state`.
   5. On any failure: restore from `hockey_legacy_backup`, surface a recovery dialog, leave the legacy blob in place.
   On a second boot where the new keys already exist, delete `hockey_legacy_backup`. No long-term migration code; a one-shot adapter with rollback.
2. **Tune annealing parameters** against a convergence fixture. ADR's 50k iterations / T₀=1000 / cooling=0.9997 are starting values, not gospel. A convergence test gates any retune.
3. **Full Phase 1 division balancing** — primary goal: allocate dates to divisions with **proportional slot budgets by team count** so the global games-per-team invariant (±1 across all teams in all divisions, PRD §3.2.2 priority 1) is achievable. Friday, Saturday, and late-slot counts are balanced as secondary tiebreaks (ADR §5.1). Current code does **neither**: it alternates A/B/A/B with token weekend balancing and never considers team count, so a division with more teams-per-slot inevitably plays fewer games per team.
4. **Drop slot-field duplication on `Game` *and* `IceSlot`.** `Game` stores only `slotId`; rendering looks up `date`/`dayOfWeek`/`startTime` via a `slotsById` selector. **`IceSlot` also drops `isLate` and `isWeekend`** — both are derived from `startTime`/`dayOfWeek` and the current `lateGameThreshold` via a `useDerivedSlots(settings)` selector. Eliminates two-sources-of-truth bugs in swap logic, in fairness-threshold changes (PRD §3.7), and on CSV re-parse after a threshold edit.

## Phase 3 — Real algorithm

The substantive payoff.

- **`dayAssignment.ts`** — proportional-target greedy assignment per ADR §5.1. Compute `target_slots[d] = round(team_count[d] × total_slots / total_teams)`; sort dates by `(slot_count desc, date asc)`; for each date assign to the division with the largest remaining budget, tiebreak on Friday/Saturday/late-slot balance, then A/B alternation. Returns `SlotsByDivision` plus a `feasibility: { ok: true } | { ok: false; reason: string }` discriminator the caller surfaces to the UI (Phase 4). This phase replaces today's `assignDatesToDivisions` (`src/lib/scheduleGenerator.ts:34-78`) which never considers team count and therefore cannot satisfy the global games-per-team invariant.
- **`scoring.ts`** — weighted score per ADR §5.3.1:
  - Late slot variance per distinct late time, squared, ×1000 *(post-v0.5: superseded by total-late aggregate ×1000 with per-slot kept as ×100 secondary — see [late-fairness-redefinition.md](./late-fairness-redefinition.md))*
  - Weekend variance squared ×100
  - Consecutive-week opponent count ×50
  - Rest-day violations (<2 days gap) ×25
  - **`maxGamesPerWeek` violations ×10000** (the currently-dead setting)
- **`slotOptimizer.ts`** — simulated annealing per ADR §5.3.2:
  - 50k iterations / T₀=1000 / cooling=0.9997 / minT=0.1 (starting values, tunable)
  - Neighbor: swap two random games within same division
  - Accept if Δ<0 OR `random() < exp(-Δ/T)`
  - Track and return best-seen solution
- **`homeAway.ts`** — standalone Phase 4: give home to team with fewer home games, **seeded** RNG tiebreak (no `Math.random()`). Independent of slot assignment.
- **Seeded RNG** — replace every `Math.random()` in `scheduler/` (including `slotOptimizer.ts`, `homeAway.ts`, `matchups.ts` shuffle, and `dayAssignment.ts` if applicable) with a mulberry32 RNG initialized from `opts.seed ?? ((Math.random() * 2**32) >>> 0)` (avoids the degenerate-zero seed from `Math.floor(...)`). Pass the `rng: () => number` function into every module that needs randomness; never call `Math.random()` from algorithm code. Store final seed on `Schedule.seed`.
- **Post-run invariants** in `scheduler/index.ts`:
  - Assert: `max(team.games) − min(team.games) ≤ 1` **across all teams in all divisions** (PRD §3.2.2 priority 1). This is the global games-per-team / cross-division balance guarantee, made satisfiable by `dayAssignment.ts`'s proportional slot allocation.
  - Assert: `max(pairCount) − min(pairCount) ≤ 1` within each division (PRD §3.2.2 priority 2).
  - On any invariant violation, **retry with a fresh seed up to 3 attempts**. If all 3 fail, surface a user-facing error in the progress overlay ("Could not produce a valid schedule — try adding/removing ice slots or check your inputs") and return the best-seen schedule with violations flagged. Do not throw silently after a 15s anneal.
  - Compute and attach to `Schedule`: pairing balance, home/away balance, week-window violations (for the fairness report to render).
- **Convergence test** — 10 runs against a 6-team / 40-slot fixture; assert mean weekend variance ≤ 1, max ≤ 2.

**Acceptance:** convergence test passes; replaying with a stored seed produces an identical `Schedule`.

## Phase 5 — Web worker + progress UI

Without this, annealing freezes the UI for 5–15s.

> **Phase-ordering note (UI-freeze gap)**: If Phase 4 (xlsx parsers) ships into `v0.5` before Phase 5, a commissioner who drops a 300-row `.xlsx` will see a frozen UI during generation. This gap is accepted because the phases ship to a long-lived `v0.5` branch (not to users) before the merge to `main`. Phase 5 must land in `v0.5` before `v0.5 → main`. If the gap becomes user-visible (e.g., a preview deploy of `v0.5`), call it out in the deploy notes.

- **Worker as thin wrapper.** `src/scheduler/worker.ts` is a Vite `?worker` import that delegates to the pure `generateSchedule(slots, teams, settings, opts?) → Schedule` exported by `src/scheduler/index.ts`. Vitest targets the pure function directly; the worker is exercised only by integration smoke tests.
- **Typed IPC.** Worker `postMessage` payloads use a TypeScript discriminated union:
  ```ts
  type WorkerMsg =
    | { type: 'progress'; iteration: number; currentScore: number; bestScore: number }
    | { type: 'done'; schedule: Schedule }
    | { type: 'error'; code: 'invariant_failed' | 'unhandled_exception'; message: string; lastBestSchedule?: Schedule };
  ```
  No `any` at the IPC boundary (Standards §1.1).
- Worker posts `progress` messages roughly every 500 iterations.
- **Worker error UI behavior.**
  - On `{ type: 'error', code: 'invariant_failed' }` (Phase 3's "3 retries exhausted" path): progress overlay shows the user-facing error message from Phase 3 plus a **"Use this schedule anyway"** button when `lastBestSchedule` is present. Clicking it writes the schedule to the store with a `hasInvariantViolations: true` flag the fairness report renders as a warning banner.
  - On `{ type: 'error', code: 'unhandled_exception' }`: progress overlay shows "Schedule generation failed. Please try again." with a **"Retry"** button. The existing schedule in the store is **retained unchanged** — never destructively overwritten on error.
  - In both cases the worker is terminated; a fresh worker is spawned on the next generate.
- `Index.handleGenerateSchedule` renders a real progress bar in the existing loading overlay using the shadcn **`Progress`** primitive (already in deps via `@radix-ui/react-progress`) and shows `bestScore` alongside.
- Surface `fairnessScore` and `seed` in the Schedule tab summary card (`ScheduleTab.tsx:135-142`). Display `fairnessScore` with a **qualitative label** mapped from the raw score:

  | Label | Score range |
  |---|---|
  | **Excellent** | `score < 5,000` |
  | **Good** | `5,000 ≤ score < 15,000` |
  | **Needs review** | `score ≥ 15,000` |

  Thresholds are starting values pinned against the 6-team / 40-slot convergence fixture (Phase 3); revisit if the fixture's mean drifts out of Excellent. Show the raw number as fine-print under the label plus a tooltip explaining the scale. PRD §1.3 target user has no coding background; raw scores alone are meaningless.
- Add a **"Reproduce this schedule"** button on the summary card. The button label avoids the word "seed" (jargon); the seed value is shown as metadata below the button (e.g., `Schedule ID: 1842735`) and an info tooltip explains that reusing the ID reproduces this exact schedule. The button is visually differentiated from "Regenerate Schedule" with a distinct icon (e.g., `RotateCcw` vs `RefreshCw`) and tooltip ("Recreate this exact schedule" vs "Discard and generate a new schedule").

**Acceptance:** UI stays interactive during generation; progress bar advances; reproducing with a stored ID yields the identical `Schedule`. **Perf assertion** (Vitest, runs in CI): the 8-team / 300-game fixture completes the configured iteration count without throwing; record `bestScore` and `iterationCount` to a baseline JSON file on first run, then assert subsequent runs stay within **±25%** of baseline on both metrics. Wall-clock is **not** asserted in CI (too flaky on shared runners); a separate local-only `npm run perf` script reports wall-clock against developer hardware as a smoke check.
