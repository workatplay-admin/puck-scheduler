# v0.5 Migration Plan — Code Meets Docs

## Goal

Bring the implementation into alignment with `docs/prd` and `docs/adr`. Every concrete claim those documents make should be verifiable in the running code.

This is a migration plan, not implementation. Sign-off on this document gates the start of Phase 0.

## Branch & PR strategy

- `v0.5` is a long-lived integration branch off `main`.
- Each phase below ships as one feature branch → PR into `v0.5`.
- Squash-merge phases into `v0.5` to keep history scannable.
- `v0.5` → `main` only after Phase 8 sign-off.

## Phase ordering

Dependency-ordered (not chronological — Phase 4 can run parallel to 2/3).

```
0. Safety net  ─►  1. Schema  ─►  2. Module split  ─►  3. Algorithm  ─►  5. Worker
                       │                                    │
                       └──────────►  4. Parsers              └──►  6. Edit parity
                                                                      │
                                                            7. Docs ──┴──► 8. Coverage
```

## Locked decisions

1. **localStorage migration on first v0.5 boot.** Single user, single browser — read legacy `hockey-scheduler-state` blob, rebuild team IDs, resolve game `homeTeam`/`awayTeam` names → IDs by lookup, write the four new keys per ADR §8, delete the old blob. No long-term migration code; a one-shot adapter that runs once and is forgotten.
2. **Tune annealing parameters** against a convergence fixture. ADR's 50k iterations / T₀=1000 / cooling=0.9997 are starting values, not gospel. A convergence test gates any retune.
3. **Full Phase 1 division balancing** — balance Friday, Saturday, *and* late-slot counts between divisions (ADR §5.1). Current code only token-balances weekends.
4. **Drop slot-field duplication on `Game`.** `Game` stores only `slotId`; rendering looks up via a `slotsById` selector. Eliminates two-sources-of-truth bugs in swap logic and when fairness thresholds change.

## Phase 1 — Schema migration

Risky data change; lands before any algorithm work so downstream phases build on the right shape.

- Replace name-keyed references with id-keyed everywhere:
  - `Game.homeTeam` → `homeTeamId`, `Game.awayTeam` → `awayTeamId`
  - matchup pool keyed by team id
  - `TeamStats.opponentGames` keyed by team id (UI joins to name)
- Drop denormalized fields from `Game`: remove `date`, `dayOfWeek`, `startTime`, `isLate`, `isWeekend`. Build a `slotsById: Record<string, IceSlot>` selector for rendering.
- Introduce wrapper: `Schedule { games: Game[]; seed: number; generatedAt: string; fairnessScore: number }`.
- Split localStorage per ADR §8: `hockey_slots`, `hockey_teams`, `hockey_schedule`, `hockey_settings`.
- One-shot migration adapter: on store init, if legacy `hockey-scheduler-state` exists and the new keys do not, migrate then delete.
- Enforce **unique team names** in `TeamsTab.handleAddTeam` (case-insensitive trim).
- Update all consumers: `ScheduleTab`, `FairnessReport`, `ExportTab`, `csvExport`.

**Acceptance:** Phase 0 snapshots pass after a snapshot-update pass for the new shape; manual smoke test of generate → edit → export.

## Phase 3 — Real algorithm

The substantive payoff.

- **`scoring.ts`** — weighted score per ADR §5.3.1:
  - Late slot variance per distinct late time, squared, ×1000
  - Weekend variance squared ×100
  - Consecutive-week opponent count ×50
  - Rest-day violations (<2 days gap) ×25
  - **`maxGamesPerWeek` violations ×10000** (the currently-dead setting)
- **`slotOptimizer.ts`** — simulated annealing per ADR §5.3.2:
  - 50k iterations / T₀=1000 / cooling=0.9997 / minT=0.1 (starting values, tunable)
  - Neighbor: swap two random games within same division
  - Accept if Δ<0 OR `random() < exp(-Δ/T)`
  - Track and return best-seen solution
- **`homeAway.ts`** — standalone Phase 4: give home to team with fewer home games, random tiebreak. Independent of slot assignment.
- **Seeded RNG** — replace every `Math.random()` in the algorithm with a mulberry32 RNG initialized from `opts.seed ?? Math.floor(Math.random() * 2**31)`. Store final seed on `Schedule.seed`.
- **Post-run invariants** in `scheduler/index.ts`:
  - Assert: `max(team.games) − min(team.games) ≤ 1` (PRD §3.2.2 priority 1) — throw on violation
  - Compute and attach to `Schedule`: pairing balance, home/away balance, week-window violations (for the fairness report to render)
- **Convergence test** — 10 runs against a 6-team / 40-slot fixture; assert mean weekend variance ≤ 1, max ≤ 2.

**Acceptance:** convergence test passes; replaying with a stored seed produces an identical `Schedule`.

## Phase 5 — Web worker + progress UI

Without this, annealing freezes the UI for 5–15s.

- Move `generateSchedule` into `src/scheduler/worker.ts` (Vite `?worker` import).
- Worker posts progress messages (~every 500 iterations): `{ iteration, currentScore, bestScore }`.
- `Index.handleGenerateSchedule` shows a real progress bar + best-score-so-far in the existing loading overlay.
- Surface `fairnessScore` and `seed` in the Schedule tab summary card (`ScheduleTab.tsx:135-142`).
- Optional: "Reproduce with this seed" button on the summary card.

**Acceptance:** UI stays interactive during generation; progress bar advances.
